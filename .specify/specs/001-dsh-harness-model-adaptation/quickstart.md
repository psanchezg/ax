# Quickstart: Validating the DSH / Non-Gemini Adaptation

**Date**: 2026-09-24 | **Plan**: [plan.md](./plan.md) | **Contracts**: [contracts/](./contracts/)

Runnable validation scenarios per user story. Implementation details live in
[tasks.md](./tasks.md) (to be generated by `/speckit-tasks`); this is the "does it
actually work" guide. All examples use placeholders — never real credentials
(Constitution: Secrets never touch the tree).

## Prerequisites

- Go 1.27 toolchain, `make`, `jq`
- Docker (for image builds, scenarios 2–4)
- A Kubernetes cluster with Agent Substrate available (for end-to-end scenarios)
- A deployed AX control plane (`ax-server`, `ax-controller`, Redis) — `make build` for
  the binaries
- A model credential in a Kubernetes secret (examples: `deepseek-api-secret` with key
  `DEEPSEEK_API_KEY`)

## 2. Phase 0 — zero-code DSH on an unmodified deployment (Story 2, FR-020)

Build the DSH runner image and apply the recipe manifest:

```bash
docker build -f Dockerfile.task-runner-dsh -t ghcr.io/<org>/ax-dsh-runner:<tag> .
cat examples/task-dsh-demo.yaml | bin/ax apply -f -   # spec.command ["dsh","--profile","headless",...], debug: true
bin/ax get task dsh-demo                              # reaches Running
bin/ax ssh dsh-demo -- ps aux | grep dsh              # DSH process visible (debug: true)
```

Expected: task reaches `Running`, DSH prints its final message on stdout; no workspace
`goal` ⇒ no Antigravity bootstrap. If the workspace binding does set a `goal` and
`GEMINI_API_KEY` is present, both harnesses run — documented caveat in
`docs/dsh-phase-0.md`. Full scenario: `examples/task-dsh-demo.yaml` +
`docs/dsh-phase-0.md`.

## 3. Model-derived credentials (Story 3)

```bash
bin/ax apply -f examples/model-deepseek.yaml -f examples/workspace-dsh.yaml
# provision a task bound to workspace dsh-ws with modelRef: deepseek
bin/ax ssh <task> -- env | grep -E 'DEEPSEEK_API_KEY|AX_MODEL_BASE_URL|AX_MODEL_YAML'
bin/ax ssh <task> -- wget -qO- http://localhost:<metadata-port>/metadata/v1alpha1/ax/model
```

Expected (contract: [container-env-contract.md](./contracts/container-env-contract.md)):

- `DEEPSEEK_API_KEY` holds the secret value (name declared by the `Model`),
- `AX_MODEL_BASE_URL` = `https://api.deepseek.com/v1`,
- `AX_MODEL_YAML` and the metadata route serve the same serialized `Model` —
  with the secretKey **reference**, never the value.

Rotation (SC-004): update the Kubernetes secret, re-provision the task, observe the new
value — no code or manifest change.

Legacy (FR-009/SC-005): provision a task with no model reference and observe
`gemini-api-secret` → `GEMINI_API_KEY` exactly as before.

## 4. Declarative harness (Story 4)

```bash
cat <<'EOF' | bin/ax apply -f -
apiVersion: ax.io/v1alpha1
kind: Workspace
metadata: {name: bad-harness, atespace: default}
spec: {harness: {kind: codex}}
EOF
# provision a task binding it with a goal
# Expected: workspace NOT Ready; condition reason UnsupportedHarness names "codex";
# setup is never silently skipped.
```

DSH happy path: `examples/workspace-dsh.yaml` (`harness.kind: deepseek-harness`,
`modelRef: deepseek`) + a task with a `goal`. Expected: runner executes
`dsh --profile headless "<goal>"` with the bound `Model`'s environment
([harness-interface.md](./contracts/harness-interface.md)).

Default preservation (SC-005/SC-009): the same manifest **without** `harness` runs
today's Antigravity bootstrap byte-for-byte — existing bootstrap tests pass unmodified.

Isolation invariant (SC-007). Measured in a cluster: the sandbox rootfs is **not**
read-only, so writing to `/etc` succeeds — what Substrate enforces is that the actor
cannot escape its sandbox (no host, no other actors, no cluster access):

```bash
bin/ax ssh <dsh-task> -- sh -c 'echo ok > /workspace/ok; echo exit=$?'   # exit=0, y es lo que sobrevive a suspend/resume
bin/ax ssh <dsh-task> -- sh -c 'echo x > /etc/pwned; echo exit=$?'       # exit=0: dentro del sandbox, pero se pierde y no da acceso al host
```

Lo que hay que comprobar es el aislamiento del sandbox (el actor no alcanza el host ni
otros actores) y que `/workspace` es la única superficie durable. Restringir el rootfs
del actor sería una mejora aparte de AX.

First boot without npm egress (SC-008): run the task on a cluster with npm registry
blocked via `Gateway` allowlist — setup completes from the pre-baked profile.

**Finding and resolution.** The first rehearsal applied only 8 of 14 patches: upstream had advanced by one commit after the fork point (`e6211f8`, "keep task templates stable across lifecycle changes"), which edits `docs/runner.md` and the same `internal/controller/reconciler.go` region this work touches. Per the constitution the fork was rebased onto `upstream/main`, which resolved both files through a three-way merge (upstream's `AX_TASK_YAML` wording and launch-config change kept, our model rows and credential block added) and surfaced one artifact: a duplicate `mockControlServer.CreateActorTemplate` in the controller test, removed inside the commit that introduced it rather than in a fixup. The exported series carries one cosmetic `git am` warning — the pre-existing adaptation proposal ends with a blank line — which does not affect the apply.

**Second finding, from the validation runbook (`docs/deepseek-harness-validation.md`, level 0.5).** Running the real `dsh` against the generated `$DSH_HOME/settings.yaml` answered `MISSING_CREDENTIAL ... llm-deepseek: no API key for provider route "deepseek-official"`: registering a provider route is not the same as selecting it, and the shipped profile mounts its own DeepSeek adapter as the default, so the agent never asked for the `Model`-named route. The harness now also writes an `agent-default-model` section. Verified against `@deepseek-ai/dsh` 0.1.5-rc.2 with a stub endpoint: DSH POSTs to the `baseURL` from the provider entry, with the credential named by `apiKeyEnv`. This is exactly the class of gap the local levels exist to catch, and it is why SC-008's "by construction" claim is not treated as verified.
